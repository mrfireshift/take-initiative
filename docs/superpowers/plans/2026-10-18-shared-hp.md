# Shared HP MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Execution method remains subject to the user's choice; no agents are dispatched by this document.

**Goal:** Auril e tre token secondari condividono gli HP, con secondari fuori iniziativa e policy danni area selezionabile per applicazione.

**Architecture:** Risolvere i gruppi con funzioni pure e preparare tutti i valori canonici nella lane autorevole esistente di `prepareEffectsMutation()`. Collegamenti, HP, History e Undo passano dallo stesso coordinatore; le UI producono intenzioni di danno/cura con importo originale e identità dell'evento. Usare la riconciliazione esistente dell'iniziativa e aggiornamenti mirati delle barre, senza watcher che propaghino danni.

**Tech Stack:** JavaScript ESM, TypeScript esistente, Owlbear Rodeo SDK esistente, Vite, `node:test`; nessuna nuova dipendenza.

**Spec:** `docs/superpowers/specs/2026-10-18-shared-hp-design.md`, approvata in chat.

## Global Constraints

- Conservare le chiavi `com.thebigpicture.initiative/meta` e `com.thebigpicture.initiative/state`.
- Conservare `meta.hp` e `meta.hpMax` come unici campi HP canonici; nessuna riserva separata nei metadata della scena o della stanza.
- Fondere sempre i metadata; preservare proprietà sconosciute, nomi di funzioni, code, revisioni, guardie di scena ed editor inline.
- Nessun riuso di `actorProfileId` per rappresentare il collegamento.
- Nessun nuovo framework o dipendenza di produzione.
- Modifiche locali e mirate in `src/initiativeList.js`, senza ristrutturarla.
- Gestione collegamenti solo GM; preservare i permessi esistenti delle normali modifiche HP.
- Default area `once`; `per-token` vale solo per l'applicazione corrente. Nessuna modifica automatica di forme o turni.

## Review Focus

1. Token senza metadata validi, HP zero, HP sopra il massimo e link interrotto: niente reset implicito o perdita di proprietà (Task 1, 3, 6).
2. Due operazioni preparate sullo stesso snapshot e retry dopo ACK perso: nessun danno perso o applicato due volte (Task 2, 5).
3. Danni superiori agli HP rimanenti e salvezze discordanti: usare importi prima del clamp e richiedere scelta esplicita (Task 1, 4, 5).
4. Collegamento del token attivo e ID virtuali vicini: stessa semantica di rimozione già presente, con tracker aperto o chiuso (Task 3).
5. Restore ActorVitals/hpMemory, gruppi misti e Undo dopo scollegamento: non divergere né ripristinare membri aggiunti dopo l'evento (Task 2, 6).

## Contracts shared by the tasks

`META_KEY` rimane quello del progetto. `Item` indica un item SDK, senza un nuovo wrapper persistente. Le funzioni pure ricevono `metadataKey` nelle opzioni, con il valore canonico come default.

- Relazione: `meta.sharedHpSourceId: string`, `meta.sharedHpExcludeFromInitiative: true` sui secondari. Nessun campo HP aggiuntivo.
- `SharedHpSelection = { policy: "once" | "per-token", chosenTargetIds: Record<sourceId, targetId> }`. Default `{ policy: "once", chosenTargetIds: {} }`.
- Un update `hp:set` o una patch metadata HP può aggiungere `hpIntent: { mode: "damage" | "heal" | "temp", amount: number, eventId: string }`. `amount` è già risolto per difese/salvezza ma non limitato dagli HP rimanenti. La forma esistente senza `hpIntent` rimane un'assegnazione assoluta.
- Il comando trasporta la scelta in `options.sharedHp`; il piano restituisce `sharedHpGroups`, con `{ sourceId, memberIds, hitIds, beforeHP, afterHP, hpMax, requestedAmount, policy, eventIds }` per gruppo. Non persistere questi riepiloghi come seconda fonte HP.
- Le UI mantengono gli stessi `commandId` ed `eventId` sui retry. Eventi distinti, anche dentro un comando, hanno ID distinti. La policy si applica separatamente a ciascun evento e riserva.
- Un risultato puro fallito è `{ status: "conflict", conflicts: [{ itemId, reason }] }`; non produce scritture parziali. Le ragioni condivise sono `shared-hp-broken-link`, `shared-hp-invalid-link`, `shared-hp-selection-required`, `shared-hp-incompatible-values`, `shared-hp-intent-required`.

## Acceptance and execution handoff

La consegna deve elencare file cambiati, comportamento disponibile, comandi eseguiti, esito build e limiti della verifica live. Non chiamare MVP completato finché restano percorsi del plugin che possono divergere o una policy area priva di controllo UI.

Metodo consigliato: esecuzione diretta nella stessa chat, perché task e test condividono i contratti del coordinatore e le modifiche si sovrappongono nei file fragili. Alternativa: esecuzione con subagenti e revisioni per task, solo dopo scelta esplicita dell'utente. In entrambi i casi, leggere le skill di esecuzione, isolamento Git, test e verifica applicabili prima di modificare codice.

## Esito della revisione finale

La revisione indipendente del ramo ha segnalato quattro problemi importanti,
corretti con test di regressione osservati prima fallire e poi passare:

- Le conseguenze automatiche a zero HP delle active spell ora derivano dalla
  proiezione condivisa del coordinatore, senza conservare gli esiti scartati
  dei singoli token (`sharedHpSpellBossIntegration.test.js`).
- Freccia Folgorante usa gli stessi contributi in anteprima ed esecuzione;
  colpo primario ed esplosione restano eventi distinti, con entrambe le policy
  e scelta esplicita in caso di TS discordanti (stesso test).
- Il runtime esistente delle barre è osservato dal background persistente.
  Il tracker mantiene le anteprime immediate senza un secondo osservatore
  della scena; opzioni e visibilità restano rispettate
  (`sharedHpMapBarsIntegration.test.js`).
- Il collegamento riconcilia le condizioni automatiche a zero HP nello stesso
  comando, senza trattare la copia degli HP come danno, con Undo completo
  (`sharedHpMutationIntegration.test.js`).

Verifica finale del codice: `npm test`, **3610/3610 PASS**; `npm run build`, **PASS**.
Collaudo live Owlbear non disponibile; la guida riporta il limite.

Decisioni di esecuzione conservate dal registro temporaneo:

1. Checkout approvato e ramo dedicato, senza nuovo worktree: mantiene il flusso
   diretto; costo se inadeguato, minore isolamento del checkout.
2. Registro in `logs/shared-hp` ignorato da Git su Windows: evita script Bash
   aggiuntivi; costo, le tracce temporanee vengono eliminate alla consegna.
3. History esistente riutilizzata per i membri espansi: Undo verificato con
   il coordinatore reale; costo se errato, ripristino incompleto del gruppo.

   struttura del tracker; costo se errato, visualizzazione non aggiornata.
5. Array `hpIntents` sulle patch unite: conserva i colpi distinti; costo,
   i producer devono mantenere correttamente gli ID degli eventi.
6. Scritture area precedenti conservate per token indipendenti: limita la
   modifica ai gruppi; costo, rimangono due percorsi HP da mantenere.
7. Helper puro per la hydration con guardie su principale e link: conserva
   l'autorità del principale; costo se errato, ripristino HP incoerente.
